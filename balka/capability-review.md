# Balka capability review

Author: Codex. Date: 2026-11-17.

## Finding

The current direction preserves the six-stage loop and its main authority boundaries, but the repository contains intents rather than an operational replacement. The missing work includes stage guidance and templates, project setup, change state, verification, controls, and the later stages. The [todo list](todo.md) captures that work without treating it as accepted scope. The [Build intent](005-ai-sdlc-build/intent.md) covers implementation planning and building against a BDD contract.

The dependency to settle before implementing this Build process is BDD in Design: the loop names acceptance scenarios, but the [Design intent](004-ai-sdlc-design/intent.md) does not yet define Gherkin, executable bindings, or evidence that new scenarios fail before implementation. The Build intent consumes that contract; the todo list records the separate Design work. The accepted Design intent has not been silently expanded.

## Review scope and sources

The primary baseline is [0.6.2](https://github.com/meteoFurletov/balka/tree/7eb07e0feb57942e14d4225d6e8442bb54ed1ae5), the last version before 0.7.0 on this branch's ancestry. The review covers its stage and supporting commands, artifact skill, templates, hook implementations, change claims, board, watcher, and test suite. It compares these with the current intents, including Build.

The [final 0.7.0 documentation work](https://github.com/meteoFurletov/balka/tree/90f575a4d847500d2e79cfbbe65084e499685e2e) was also checked for subsequent fixes worth preserving. A [separate 0.7.0 maintenance branch](https://github.com/meteoFurletov/balka/commit/7e3ce38588018ec4881cff6a1200f437a5d2bd3f) changed Stage 6 in another direction; it was not merged into that documentation line. Its maintenance proposal is an option to consider in a future intent, not an accepted requirement of the new Balka.

The older personal-OS branch is outside this SDLC comparison. No historical implementation was restored or installed in the project.

## What the new direction retains

The [harness-independence intent](001-harness-independence/intent.md) retains portable process, project knowledge, change state, operations, and controls. The [loop intent](002-ai-sdlc-loop/intent.md) retains one owner, separate acceptance of intent, design, and implementation plan, autonomous Build and Test within accepted scope, return to earlier stages for contract changes, documentation maintenance, and evidence distinctions. The [Plan intent](003-ai-sdlc-plan/intent.md) and Design intent cover clarification, review, and acceptance as outcomes, but do not yet supply executable operations or reusable templates.

The Build intent retains the historical planning and implementation flow: inspect the real repository, name the scenarios and files, record risks and rollback, obtain acceptance, build until applicable checks pass, record departures with the change, and continue into independent Test. These are process requirements; their acceptance does not establish implemented capabilities.

## Historical mechanisms to redesign

The scenario hooks did not establish the full BDD guarantee. Any draft spec opened edits to existing scenarios, any staged spec satisfied the scenario commit check, and newly created scenario files passed both checks. Expected-result assertions in binding files were left to instructions and later review. The new controls need change-specific contract boundaries rather than inheriting these checks as sufficient enforcement. These limits follow directly from the linked hook implementations; the old suite's passing cases do not test them away.

Plan synchronization checked paths, not whether the implementation followed the approach. It accepted any staged plan update and stayed inactive when no accepted plan existed. The shared hook machinery also allowed actions when it could not establish a condition. Those choices may have suited advisory checks, but they cannot be imported as guarantees that mandatory boundaries hold.

The watcher compared the text of Git status before and after diagnosis, which does not prove file contents stayed unchanged when the same paths remain modified. Its recovery used a broad checkout of tracked files, which could discard pre-existing work. A future diagnosis operation needs a deliberate isolation and write-authority design. This is a code-review finding, not a reproduced runtime incident.

The documentation line corrected a contradictory completion instruction: Test must update the plan header's existing status rather than add a second status under Departures, because the board and controls read the header. The general lesson is one authoritative state record, with explicit meaning for accepted, verified, delivered, and observed work.

## Work order

Complete the core loop stage intents first, including BDD's Design contract, Build, Test, Deploy, and Maintain. Then address project knowledge, reusable guidance, controls, and parallel work, in that order and through their own intents.

Other supporting work follows: process guidance and operations, project adoption, change state, change sizing, verification setup, process feedback, work visibility, and verification of Balka itself. The old implementation supplies examples and test cases for these decisions; it does not choose the new architecture.

## Validation and limits

Both historical snapshots were exported into temporary directories and their existing offline suites were run without changing this checkout: 0.6.2 and the documentation-line 0.7.0 each reported `76 passed, 0 failed`. The suite exercises hook decisions, path matching, local change claims, board behavior, and watcher detection. It does not execute the agent-facing stage commands as an agent or prove the semantic correctness of their guidance. The documentation Gherkin files explicitly describe manual acceptance review because that repository has no scenario runner.

The current branch has no executable Balka implementation or test suite. The changes in this review are documentation, a Build intent, and future-work entries; they have not implemented BDD, controls, or the missing stages.
